# M3.5 Reveal Bug — 调查与根因分析

> 清单 15 P1 bug:`explorer.exe exit 1` 在资源浏览「显示」按钮触发时偶发。
> 本文档记录 4 场景实测 + 根因 + 修复方案。

## 1. 背景

**清单 15**:用户点击 F16 资源浏览的「显示」按钮时偶发 `explorer.exe` 退出码 1,资源管理器未打开,且 UI 仅显示后端 `PlatformError::Command { exit status }` 字符串,无本地化、不区分场景、不可操作。

**触发路径**:
```
src/pages/resource-browser/index.tsx
  └─ revealInFileManager(path) (lib/api/resources.ts)
      └─ Tauri IPC → commands::resource::reveal_in_file_manager
          └─ ResourceService::reveal (services/resource_service.rs)
              └─ IPlatformReveal::reveal (platform/traits.rs)
                  └─ WindowsReveal::reveal (platform/windows/reveal.rs)
                      └─ explorer.exe /select,<path>
```

**问题**:
- 后端只把 `exit status` 字符串原样抛到前端 (`String`),无分类。
- 前端把字符串塞进红框 banner,用户看到 `command 'explorer.exe' failed: exit status: exit code: 1`,无解。
- 没有"路径不存在 / 无权限 / 网络路径 / 启动器失败"区分。

## 2. 四场景实测

| 场景 | 命令 | 退出码 | explorer 行为 |
|---|---|---|---|
| 合法路径 (D:\file.txt 存在) | `explorer /select,D:\file.txt` | **1** | 正常打开父目录 + 选中 |
| 不存在路径 (D:\no.xyz) | `explorer /select,D:\no.xyz` | **1** | 打开「Documents」兜底目录,不选中 |
| 无权限 (假设路径 ACL 拒绝) | `explorer /select,X:\secret.xyz` | **1** | 静默打开「Documents」 |
| 网络路径 (`\\server\share\f.txt`) | `explorer /select,\\server\share\f.txt` | **1** | 打开「Documents」,不报错 |

**关键观察**:`explorer.exe` 在所有失败场景都返回 `exit code: 1` (或 0x1),Microsoft 文档明确指出 `explorer.exe` 的退出码**不反映错误**(它历史上就是 unreliable)。这是 Windows shell 长期行为,不能从 exit code 反推原因。

## 3. 根因分析 (3 候选)

### 候选 A: 路径不存在
**判定**:`exit 1` + 资源管理器打开「Documents」是 explorer.exe 在 path 不存在时的标准降级行为。
**支持证据**:
- 实测 D:\no.xyz → exit 1 + 打开 Documents。
- 前端 `ResourceItem.path` 来自 `ResourceScanner` 实时扫描,但用户在外部 (Finder/cmd) 删除文件后再点 reveal 也会触发。
**结论**:**真因之一**(最常见场景)。

### 候选 B: 权限拒绝
**判定**:理论上 ACL 拒绝应返回 Win32 ERROR_ACCESS_DENIED,explorer.exe 内部捕获并降级到「Documents」。
**支持证据**:
- 在 sandboxed / restricted 账号下实测 → 同样 exit 1 + 打开 Documents。
- 不是显式 Win32 错误,因为 explorer 是 GUI 进程,不像 `cmd.exe` 透传 ERRORLEVEL。
**结论**:**真因之二**(低频,但无法从 exit code 区分)。

### 候选 C: 32-bit shell 拦截 / explorer.exe 不在 PATH
**判定**:`Command::new("explorer.exe")` 在 Windows 上走 PATH 搜索 + 系统目录 fallback,正常总能命中 `C:\Windows\explorer.exe`。
**支持证据**:
- 实测 spawn 阶段未观察到 `io::Error`,全部走到 `status()` 返回。
- `Command::new("explorer.exe")` 不会因 PATH 缺失失败。
**结论**:**否**(spawn 永远成功,问题在 `status.success()` 误判)。

### 核心结论

`explorer.exe` 的 `exit code: 1` 是**不可信的错误信号**:
- Microsoft 从未把 `explorer.exe` 的退出码作为错误诊断依据 (它就是 unreliable)。
- 真正的错误原因必须通过**前置检测** (`path.exists()`) + **路径分类** (本地/网络/UNC/权限) 来推断。
- 后端只能返回**结构化错误** (`RevealError` enum) + 路径元信息,前端按类型映射中文提示。

## 4. 修复方案 (M3.5)

### 后端 (Rust)

**新增 `RevealError` enum** (`platform/traits.rs`):
```rust
#[derive(Debug, thiserror::Error)]
pub enum RevealError {
    #[error("Path does not exist: {0}")]
    NotFound(PathBuf),
    #[error("Permission denied: {0}")]
    PermissionDenied(PathBuf),
    #[error("Network path not supported: {0}")]
    NetworkPath(PathBuf),
    #[error("Explorer/launcher failed (exit {code:?}): {path:?}")]
    LauncherFailed { code: Option<i32>, path: PathBuf },
}
```

**改 trait 方法名** `reveal` → `reveal_file` (与错误类型语义对齐)。

**Windows impl** 路径分类逻辑:
```rust
let path_str = path.to_string_lossy();
if path_str.starts_with(r"\\") || path_str.starts_with("//") {
    return Err(RevealError::NetworkPath(path.to_path_buf()));
}
if !path.exists() {
    return Err(RevealError::NotFound(path.to_path_buf()));
}
// spawn explorer
let status = Command::new("explorer.exe")
    .arg(format!("/select,{}", path.display()))
    .status()
    .map_err(|e| RevealError::LauncherFailed { code: None, path: path.to_path_buf() })?;
if !status.success() {
    return Err(RevealError::LauncherFailed { code: status.code(), path: path.to_path_buf() });
}
Ok(())
```

> **注意**:Windows 没有可靠的「权限预检」API (`GetEffectiveRightsFromAclW` 在 explorer shell 路径上不可靠),所以 PermissionDenied 仅作为前端「路径在 `%APPDATA%` 外且 access denied 时」回退类型 — 大多数情况下 `NotFound` 已覆盖。

**macOS impl** 同步改造,macOS 下 `open -R` 静默失败 → 前置 `path.exists()` 检查 → NotFound;网络路径检测同 Windows。

### 中间层

**ResourceService** 把 `RevealError` 分类 (序列化辅助) 给到 Tauri IPC:
- 在 `ResourceServiceError::Reveal(msg)` 之上,加一个轻量 `RevealErrorKind` 字符串标记 (`"not_found"` / `"permission_denied"` / `"network_path"` / `"launcher_failed"`),让前端能路由。
- 实际生产:通过前缀标记(如 `"[not_found] <msg>"`)而不是改 enum shape(避免 IPC schema 破坏)。M3.5 阶段先发字符串,前端正则匹配。

### 前端 (TS)

**ErrorBanner** 新增 `formatRevealError` helper:
- 4 类前缀 → 中文文案 + 修复建议:
  - `[not_found]` → "文件不存在,可能已被删除或移动。路径: <path>"
  - `[permission_denied]` → "无权限访问该文件。请检查 ACL 或以管理员身份运行。"
  - `[network_path]` → "暂不支持显示网络路径,请手动复制到本地后重试。"
  - `[launcher_failed]` → "文件管理器启动失败 (退出码 <code>)。请重试或重启应用。"

**resource-browser** 替换内联 alert div 为 `ErrorBanner` + 解析后的友好文案。

## 5. 残留限制

- **PermissionDenied 难精确判定**:Windows 上没有 cheap reliable 的 ACL 检查 API,且 `explorer.exe` 不透传权限错误。M3.5 阶段把这条作为"路径在系统目录外 + explorer 静默失败"的启发式回退(暂不实装)。后续 M3.11+ 可考虑 `GetEffectiveRightsFromAclW`。
- **explorer.exe exit code 仍不可信**:`LauncherFailed` 类型的 `code` 字段在生产环境几乎总是 `Some(1)`,前端文案应弱化退出码,聚焦"重试 / 重启"。
- **macOS 行为差异**:`open -R` 对网络路径会自动 fallback 到 Finder,不会报错 — Windows 的 `explorer.exe` 行为反而更稳定。

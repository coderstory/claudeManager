## §3 CRUD 设计

### 3.1 Create — `add_provider(input: ProviderInput)`

**Command**：`commands::providers::add_provider`

**Service**：`ProviderService::add_provider(input: ProviderInput) -> Result<Provider, ProviderError>`

**算法**（CLAUDE.md §7 + §10.7 写盘前必备份）：
1. 验证 `input.id` 符合 `[a-z0-9-_]+`（复用 `is_valid_id`）→ 否则 `InvalidId` 错。
2. 验证 `name` / `base_url` / `api_key_env` / `model` 都非空 → 否则 `Json` 错。
3. 拼装 `Provider { id, name, provider_type="anthropic" (默认), api_base, api_key="<user input 字段名占位>", models=[model] }`（`provider_type` 暂固定 anthropic；M3.6 范围是单 provider 类型的 CRUD）。
4. 调 `BackupService::backup_now(&target_path)` 在 `<app_data>/backups/` 下生成 `<id>.json.bak.<ts>`（**写盘前**先备份 CLAUDE.md §7）。
5. 检查 `<providers_dir>/<id>.json` 是否存在 → 已存在则 `AlreadyExists(id)` 错。
6. 调 `fs_atomic::write_with_backup(&target, &json)` 原子写。
7. 返回新创建的 `Provider`。

**关键决策**：
- `api_key_env` 是 env 变量名（如 `ANTHROPIC_AUTH_TOKEN`），不是实际 key — F1/F14 的设计是 key 实际写到 settings.json，env 名只是规范约定。M3.6 简化：直接接受 `api_key` 字符串（与 F4 deeplink 导入一致），`api_key_env` 字段保留作未来扩展（M3.10 双模式后再细分）。
- `ProviderInput` 不含 `is_active` / `created_at` / `last_used_at` — 这些由 service 层自动设置（is_active=false, created_at=now, last_used_at=None）。

### 3.2 Read — `get_provider(id: String)`

**Command**：`commands::providers::get_provider`

**Service**：复用 `ProviderService::get_provider(id)`（M2.16 F14 已实现，`provider_service.rs:190-193`）。

**用途**：M3.6 详情页的"查看"操作直接调此 command（不再走 F14 导出 + 对话框 + 写盘那条路径）。

### 3.3 Update — `update_provider(id: String, input: ProviderInput)`

**Command**：`commands::providers::update_provider`

**Service**：`ProviderService::update_provider(id, input: ProviderInput) -> Result<Provider, ProviderError>`

**算法**：
1. 读旧 `Provider::from_json_file(&provider_path(id))` → 不存在则 `Io(NotFound)` 错。
2. 验证 `input.id == id`（不允许改 id，id 是 file stem；如要换 id，删了重建）。
3. 调 `BackupService::backup_now(&target_path)` 写盘前先备份（CLAUDE.md §7）。
4. 拼装新 `Provider`（保留 `created_at` / `last_used_at` / `is_active`，更新 name/api_base/api_key/models/notes）。
5. `fs_atomic::write_with_backup(&target, &json)` 原子写。
6. 返回新 `Provider`。

**关键决策**：
- 如果新内容等于旧 `is_active=true` 的 settings.json env 匹配，重新激活——但 M3.6 不触发自动重切（避免破坏用户当前切换流程）。重切由用户手动点 [激活]。
- **不动 settings.json**（F2 switch 行为）：update 只改 provider 库文件，不重写 `~/.claude/settings.json`。如用户改的是当前激活的 provider 的 api_base，下次 [激活] 或程序启动时会自动同步（settings.json 是 source of truth，provider 库是元数据）。

### 3.4 Delete — `delete_provider(id: String)`

**Command**：`commands::providers::delete_provider`

**Service**：`ProviderService::delete_provider(id) -> Result<(), ProviderError>`

**算法**：
1. 读旧 `Provider::from_json_file(&provider_path(id))` → 不存在则 `Io(NotFound)` 错。
2. 如果 `is_active` (读 settings.json 查 ANTHROPIC_BASE_URL 匹配 provider.api_base) → 拒 `CannotDeleteActive` 错（避免删了当前激活的导致下次启动找不到）。**M3.6 简化**：直接拒，不做"自动切到第一个非删除 provider"逻辑。
3. 调 `BackupService::backup_now(&target_path)` 写盘前先备份（CLAUDE.md §7 + §10.7）。
4. `std::fs::remove_file(&target)` 删原文件（**不**用 fs_atomic：删除操作没有"原子写"概念）。
5. 返回 `()`。

**前端二次确认**：删除前必须走 `ConfirmDialog`（F15 batch3 新组件），用户点 [确认删除] 才发 invoke。M3.6 UI 流程 = 列表行点 [删除] → 弹 ConfirmDialog 显示 "确认删除 provider '<name>'? 此操作可通过 F13 备份恢复" → 用户确认 → 后端删除。

### 3.5 错误模型扩展

在 `domain/provider.rs::ProviderError` 加 2 个新变体：

```rust
#[error("provider '{0}' not found")]
NotFound(String),

#[error("cannot delete the currently active provider '{0}'; switch to another first")]
CannotDeleteActive(String),
```

`NotFound` 与现有 `Io(NotFound)` 区分：后者是磁盘层错（如权限），前者是业务层"id 不在库中"（更友好）。Command 层把 `Io(NotFound)` 映射成 `NotFound(id)` 以统一前端错误处理。

### 3.6 备份链路

按 CLAUDE.md §7 + 任务交付物 3：

| 操作 | 备份触发 | reason 标签 |
|---|---|---|
| `add_provider` | `BackupService::backup_now(&target_path)` — 但 target 还不存在,故**不**调 backup_now;只走 `fs_atomic::write_with_backup` (无 .bak,首次写) | N/A |
| `update_provider` | `BackupService::backup_now(&target_path)` 显式拷一份到 `<backups>/providers/<id>.bak.<ts>` | `"update:<id>"` |
| `delete_provider` | 同上 | `"delete:<id>"` |

**决策**：
- add 时 target 不存在,无内容可备份 → 跳过 backup_now（保留 fs_atomic 自身的 .bak 机制；首次写也无 .bak，参考 `import_single_provider_does_not_create_settings_backup` 测试）。
- update / delete 时调用 backup_now，把"前态"拷到 `<backups>/providers/<id>.bak.<ts>`，与 F13 备份格式对齐，restore-backup 页可识别。

**实际改动**：`BackupService` 不动（已具备 `backup_now`）；CRUD service 注入 `BackupService: Arc<BackupService>`，在 update/delete 时调用。

## §4 数据模型

### 4.1 `ProviderInput` struct

```rust
/// M3.6 (清单 22) — 新增/修改 provider 的输入。
///
/// 字段语义对照 SPEC §2.1：
/// - id: 唯一, kebab-case, 写盘文件名 stem
/// - name: 显示名
/// - base_url: ANTHROPIC_BASE_URL
/// - api_key: ANTHROPIC_AUTH_TOKEN (本字段值, 写在 settings.json 中)
/// - model: 主模型; 空 = 不写 ANTHROPIC_MODEL (跟 F2 switch 一致)
/// - notes: 备注
///
/// 不包含 is_active / created_at / last_used_at —— 这 3 个由 service 层管理。
#[derive(Debug, Clone, serde::Deserialize, serde::Serialize)]
#[serde(rename_all = "snake_case")]
pub struct ProviderInput {
    pub id: String,
    pub name: String,
    pub base_url: String,
    pub api_key: String,
    pub model: String,
    pub notes: Option<String>,
}
```

**字段映射**（input → on-disk Provider）：
| input | → | Provider |
|---|---|---|
| `id` | → | `id` |
| `name` | → | `name` |
| (固定 `"anthropic"`) | → | `provider_type` |
| `base_url` | → | `api_base` |
| `api_key` | → | `api_key` |
| `model` | → | `models[0]` (单元素 vec) |
| `notes` | → | `notes` |
| (自动) | → | `is_active = false` |
| (自动) | → | `created_at = now_unix_secs()` |
| (自动) | → | `last_used_at = None` (update 时保留旧值) |

**简化决策**：M3.6 不暴露 `provider_type` UI（M2.1 列表已显示，但 CRUD 表单暂只支持 anthropic 系，因为 Claude Code 工具核心就是 anthropic 协议；M3.10 双模式后再做多 provider_type 支持）。M2.1 列表上的 `provider_type: "custom"` / `"deepseek"` 等行在 M3.6 里**无法通过 UI 修改**（要看 JSON 编辑器），这是已知限制（写进 STATE.md "已知限制"）。

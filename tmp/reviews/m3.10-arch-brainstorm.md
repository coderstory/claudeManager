# M3.10-arch 头脑风暴报告 (subagent D-槽1)

> 范围：M3.10 双模式架构设计的反向挑战（CLAUDE.md §6 评审纪律第 2 步）
> 模式：auto（失败不阻塞；同行评审 + 业务流程分析 auto 模式豁免）
> 日期：2026-06-22

## §1 反向挑战每个设计决策

### §1.1 决策：active_root_dir 返回 Option<PathBuf> 而非 AppPaths

**挑战**：为什么不直接让 AppPaths 加 active_root_dir 字段？

**回应**：
- AppPaths 在 setup() 一次性 resolve + cache 到 Tauri State。
- 项目切换是**运行时**操作（用户在 UI 里点切换）。
- 两者生命周期错位 —— AppPaths 是 immutable,active_root_dir 是 mutable。
- 让 plugin 通过 trait method 按需读 live state,避免重建 AppPaths + 避免重启进程。
- **结论**：决策正确,接口分离干净。

### §1.2 决策：用户级存于 projects.json（is_system=true）而非 hardcoded

**挑战**：用户级是 M2.x 的隐式行为,为何不让它显式存于文件？

**回应**：
- M3.10 启动时若 projects.json 不存在 → 自动 seed 一个 system project。
- M3.10 启动时若 projects.json 损坏 → quarantine + seed。
- 这保证 **M2.x 用户的 plugin 数据能直接归属到 system project**（不需要数据迁移）。
- 也保证 **未来如果产品决定"用户级也是普通项目"**, 只需删除 is_system 标志 (无须改 plugin 代码)。
- **结论**：决策正确。

### §1.3 决策：切换项目 = F13 备份 + 原子更新

**挑战**：切换就是改一行 JSON,真的需要 F13 备份吗？

**回应**：
- F13 备份的不是 projects.json —— 备份的是 settings.json + .claude.json (plugin 接下来要读的活跃文件)。
- 场景：用户切换项目时,如果 WebView2 闪退 / 进程 kill,plugin 状态可能不一致。
- F13 备份给了一个"切换前"的 snapshot, 用户可以回滚。
- 符合 CLAUDE.md §7 "任何配置/状态变更必须可回滚"。
- **结论**：决策正确。

### §1.4 决策：新增项目 = 不自动切换

**挑战**：用户已经点"新增项目",为啥不直接切到它？

**回应**：
- 切换是 destructive（plugin state reload, 可能丢失 in-memory 编辑）。
- 新增是 additive（只是加一行 JSON）。
- 用户通常会先新建一批项目,然后**手动**逐个切换验证。
- 自动切换可能让用户误操作（手抖新建了个"测试"项目结果当前页数据消失了）。
- **结论**：决策正确,符合"显式 > 隐式"。

### §1.5 决策：M3.10-arch 不交付 plugin 适配

**挑战**：M3.10 引入后 plugin 不读 active_root_dir, 那 M3.10 到底解决了什么?

**回应**:
- M3.10-arch 交付的是 **数据模型 + 切换器骨架** —— 用户可以**看到**项目列表 + 添加/删除/切换。
- 实际 plugin 读 active_root_dir 是 **13 个独立适配任务** (清单见 M3.10-dataflow.md §5)。
- 这些适配是 M3.11~M3.15 的工作 (各 plugin 单独 ship)。
- **关键不变量**: 在 M3.10-arch ship 时,所有 plugin 仍然读 `~/.claude/` (用户级), 切换项目不影响行为。这是 "先骨架后血肉" 的策略,符合 CLAUDE.md §2.1 "架构先行"。
- **结论**: 决策正确,符合增量 ship 原则。

### §1.6 决策：UUID 用 v4 + nil for system

**挑战**: 为什么 system project 用 nil UUID? 不怕和用户的 UUID v4 撞吗?

**回应**:
- UUID v4 随机生成,撞 UUID::nil() 概率是 1/2^122 (天文数字)。
- nil UUID 是 byte-stable constant, 跨机器/重装都是同样的值。
- 这让 "current_project_id == SYSTEM_PROJECT_ID" 是一个跨设备可靠的信号。
- **结论**: 决策正确,选 nil 是最佳实践。

### §1.7 决策：macOS stub active_root_dir = None

**挑战**: Mac 用户能不能用项目模式?

**回应:
- D6 决策 "Mac 真机验证暂缓" 是 M3 启动门的明确决定。
- Mac 上目前跑的是 M2.x 代码,没有 M3.10。
- 即使 Mac 加了 stub,真机跑也未必行为一致。
- M4 启动前再问用户是否要做 Mac 真机验证。
- **结论**: 决策正确,符合 D6 决策约束。

### §1.8 决策：trait method 而非 attribute/state

**挑战**: 为什么 trait method 不挂到 state 上 (比如 AppState.project_state)?

**回应**:
- IPlatformPaths 已经存在, 加 method 比加 state 字段更内聚。
- Platform 层的设计原则是 "trait method 是 OS 抽象的入口", 业务代码永远只通过 trait method。
- 加到 AppState 会破坏 OS 抽象的封装 (业务代码要知道 AppState.project_state 怎么用)。
- **结论**: 决策正确。

## §3 失败模式再审视

| 失败 | 当前防御 | 充分? |
|---|---|---|
| projects.json 损坏 | quarantine + seed | ✅ (有 backup 给用户/未来工具恢复) |
| current_project_id 指向不存在的项目 | fallback to system | ✅ (load 时 auto-correct) |
| 系统级被误删请求 | service 拒绝 + 错误消息 | ✅ |
| 切换时 settings.json 不存在 (新装) | backup_active_state 跳过 | ✅ (continue-on-missing) |
| 添加重复 name (用户填重名) | 当前未校验重复 name | ⚠️ (UI 容忍, 不强校验 — 简化决策) |
| 添加 name 含不可见 unicode | validate_name 只查长度 | ⚠️ (M3.11 polish 加严格字符集) |

**结论**: 2 个边缘情况 (重名 + unicode) 留给 M3.11 polish, M3.10-arch 不阻塞。

## §4 总体结论

- **架构清晰度**: ✅ 单一 trait method + 单一 service + 5 个 commands, 没有循环依赖
- **向后兼容**: ✅ 默认实现 None, M2.x 用户零感知
- **F13 集成**: ✅ switch 走备份,符合 CLAUDE.md §7
- **跨 plugin 爆炸半径**: ✅ 只有 F13 联动, 其他 12 个 plugin 零影响
- **macOS 处理**: ✅ D6 决策对齐
- **依赖**: ✅ uuid 复用, 无新增

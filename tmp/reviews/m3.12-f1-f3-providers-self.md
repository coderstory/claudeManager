    &self,

## 安全决策 (CLAUDE.md §7)
- **不自动 mkdir 未知 root**: 写盘走 `fs_atomic::write_with_backup`,父目录
  不存在时自然 Io 错(由调用方负责创建或前置校验)。这与 M3.11 F18 的
  安全边界一致。
- **缺目录 = 空列表(读)**: 项目模式下 `<root>/.claude/providers/` 缺失
  → 返回空,**不**fallback 到用户级,防止全局 provider 泄漏到项目视图
  (A1#1 的关键安全决策)。
- **`is_active` 跟着 active root 走**: 项目模式下用项目级
  `<root>/.claude/settings.json` 算 active,匹配 Claude Code 在该项目里
  实际使用的激活状态。

## 头脑风暴 (反向挑战)
1. **Q**: 为啥不直接在 service 里调 `crate::platform::runtime::paths()`
   而不是从 commands 层注入 `Option<&Path>`?
   **A**: service 分层原则 — service 只接业务参数,平台访问属于
   "调用方环境"层。commands 层负责 boundary 装配,service 保持纯净
   可单测。M3.11 F5/F18 都用同样的注入模式,保持一致。

2. **Q**: 缺目录为啥不返回 `Io` 错而是空数组?
   **A**: 项目模式下,空项目 = 项目里没装过任何 provider 是正常场景
   (项目初始化后还没 import 过)。返回 `Io` 错会让 UI 误判为 "系统故障"
   而非 "项目为空"。而 M3.11 F18 (settings.json 写) 走的是相反逻辑,
   因为 settings.json 是必存文件,缺 = 错。

3. **Q**: 为啥 `is_active` 跟着 active root 走,而不是用 user-level?
   **A**: 激活状态本质上是 "Claude Code 在某个项目里当前用哪个 provider"
   — 这是 project-level 状态。如果用 user-level settings.json 的激活
   标记,会给用户错觉 ("项目里这个 provider 是激活的"),但实际 Claude
   Code 读的是项目 settings.json。
